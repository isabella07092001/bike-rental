# Phase 1 – Bike Management: Requirements

Status: **Implemented** (2026-11-06)

## Context

Alice and Bob need to maintain their bike fleet in the system before reservations (Phase 3)
can be built on top of it. Each bike belongs to exactly one category, and the category
determines the hourly rental price (see [mission.md](../mission.md), Business Rule 3).

This phase builds on the Phase 0 skeleton: Go server with router in `internal/handler`,
empty `internal/domain` and `internal/store` packages, and the HTML shell in `web/`.

## Scope

### In scope

- Domain model for `Bike`, `Category` and `Status`, including the hourly price per category
- Thread-safe in-memory store for bikes behind a `Store` interface
- JSON API for creating, listing, reading, updating and retiring bikes
- "Bikes" page in the frontend: list, create/edit form, retire
- Tests for domain, store and handlers

### Out of scope

- Reservations, availability calculation and the "rented" state (Phase 3)
- Blocking retirement of bikes with future reservations (added in Phase 3)
- Dashboard figures (Phase 4)
- Bike photos, frame size, frame number, maintenance history
- Editing category prices through the UI
- Persistence across restarts

## Domain Model

### Category

Fixed set of four values. Prices are **placeholders** until the stakeholders confirm them;
they are defined in one place in `internal/domain`.

| Value | Label | Hourly price |
|-------|-------|--------------|
| `children` | Children's bike | 4.00 € (400 cents) |
| `city` | City bike | 6.00 € (600 cents) |
| `mountain` | Mountain bike | 9.00 € (900 cents) |
| `racing` | Racing bike | 10.00 € (1000 cents) |

- `Category.Valid()`, `Category.Label()`, `Category.HourlyPrice()` (cents)

### Status

| Value | Meaning |
|-------|---------|
| `available` | Bike can be rented (default for new bikes) |
| `maintenance` | Bike is temporarily out of service |
| `retired` | Bike is permanently out of the fleet; kept for history, hidden by default |

### Bike

| Field | Type | Rules |
|-------|------|-------|
| `ID` | string | assigned by the store, not editable |
| `Name` | string | required, trimmed, max. 100 chars, unique (case-insensitive, also among retired bikes) |
| `Category` | Category | required, one of the four values |
| `Status` | Status | defaults to `available` |
| `Description` | string | optional free text (color, brand, notes), trimmed, max. 500 chars |

`Bike.Validate()` returns a wrapped `ErrInvalid` describing the first violated rule.

## API

| Method | Path | Success | Errors |
|--------|------|---------|--------|
| `GET` | `/api/bikes` | `200` list of non-retired bikes; filters `?category=`, `?status=` (`?status=retired` shows retired bikes) | `400` invalid filter value |
| `POST` | `/api/bikes` | `201` created bike | `400` validation, `409` duplicate name |
| `GET` | `/api/bikes/{id}` | `200` bike (also when retired) | `404` |
| `PUT` | `/api/bikes/{id}` | `200` updated bike | `400`, `404`, `409` |
| `POST` | `/api/bikes/{id}/retire` | `200` bike with status `retired` | `404` |
| `GET` | `/api/categories` | `200` categories with value, label and hourly price | – |

- There is no hard delete; bikes are retired instead.
- A retired bike can be reactivated by setting its status via `PUT`.
- Error responses use the shape `{"error": "<message>"}`.

## Frontend

- Table of bikes: name, category, hourly price, status, description, actions (edit, retire)
- Toggle "show retired bikes"
- Form for create and edit (name, category dropdown filled from `/api/categories`, status,
  description)
- Retire asks for confirmation
- Validation errors from the API are shown next to the form

## Decisions

| # | Decision | Reason |
|---|----------|--------|
| D1 | Categories are a fixed enum in code, not a managed entity | Four stakeholder-defined categories; simplest model for a prototype |
| D2 | Hourly price is per category, with placeholder values (4/6/9/10 €) | Matches Business Rule 3; real prices still to be confirmed by stakeholders |
| D3 | Prices stored as integer cents | Avoids floating-point rounding errors in price calculation |
| D4 | Bike fields: ID, name, category, status, description | Chosen by product owner; frame size/number not needed for now |
| D5 | Bikes are retired (status `retired`), never hard-deleted | Keeps history; reservations in Phase 3 can still reference old bikes |
| D6 | Bike names are unique (case-insensitive), including retired bikes | Name identifies the physical bike in the shop; avoids confusion |
| D7 | IDs generated by the store | Keeps the domain free of ID logic; handlers never invent IDs |
| D8 | Store interface introduced now | Only planned interface (see tech-stack.md); enables later DB swap |
| D9 | Standard library only (`net/http`, `encoding/json`, `sync`) | No new dependencies without asking |
